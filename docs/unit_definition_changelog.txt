(#1177, no version raise -- no new property)
- RadioButtonGroupElement: styling.lineHeight stored in a unit now survives loading.
  Before, normalization dropped the stored value (the radio defaults entry had no
  lineHeight, so the styling lift skipped the key) and the model forced 100 on every
  load -- user-set line heights silently reverted. With lineHeight: 100 in the radio
  defaults the stored value is preserved; units that never changed it keep rendering
  with 100 as before.

(#1190, no version raise -- no new property)
- Units stored with a version between 4.0.0 and 4.9.x keep their data on loading.
  MigrationLegacy converts the 3.10 shape to the 4.0 shape, but declared
  toVersion 4.10.0, and the step filter reads that declaration -- so it also ran
  over units that already carried the 4.x shape. Three of its transformations have
  no guard against being handed the new shape and overwrote what they found:
  dimensions was rebuilt from the flat width/height removed in 4.0.0 (the element
  defaults then won), visibilityRules became [] and animatedVisibility false because
  activeAfterID no longer exists, and addInputAssistanceToKeyboard was set from the
  softwareKeyboardShowFrench removed in 4.0.0. With toVersion 4.0.0 the step no
  longer reaches those units; they are brought up to date by NormalizationMigration,
  which runs regardless of the filter, exactly as before.

(#1184, no version raise -- no new property)
- Elements no longer share their margin objects with the defaults table.
  PropertyGroupGenerators.generatePositionProps returned the marginLeft/Right/Top/Bottom
  object it was given, and it is usually given an ELEMENT_DEFAULTS entry -- so every
  element built without a stored margin of its own held the registry's Measurement,
  shared with the table and with every other element of that type. Nothing broke: every
  writer replaces the margin object rather than editing it, so the sharing stayed
  invisible. The generator now copies, which closes the hole before the first in-place
  write appears. Margin values are unchanged; what changes is object identity, and one
  edge case -- a stored margin that is not an object at all (an explicit null, say)
  used to come back out unchanged and is now an empty object.

(#1187, no version raise -- no new property)
- Frame, audio and video no longer carry font styling. Their styling declares border
  and background (frame) or background alone (audio, video) and no font member at all,
  but normalization added fontColor, font, fontSize, bold, italic and underline to every
  element on load, whatever its type -- so the inspector offered these three element
  types five controls that render nothing (font colour, font size, bold, italic,
  underline), and the keys were saved back into the unit. Which styling keys an
  element keeps is now decided by the group its own class builds, which the compiler
  checks against the declared type. Font values stored on one of the three are dropped
  on the next load; nothing renders them, so nothing changes on screen. The other 27
  element types keep exactly the styling group they had.
  Not covered, because their styling type does not say so: image, geometry, trigger,
  hotspot-image, marking-panel and likert-row declare no styling of their own and
  therefore keep the basic group the base class builds, although none of their
  components reads it either. Their controls are as dead as the three above; narrowing
  their declaration is a decision about the inspector and is filed separately.
- A stored styling value now survives for every key an element declares. Before, the
  group was rebuilt from four hand-kept lists, and a key no list named was dropped even
  though interface and defaults table both declared it (#1177 for radio.lineHeight,
  #1185 in general). No unit needs repairing: what was dropped was never stored.

(#1182, no version raise -- a property is retired, none is added)
- styling.font is gone from the model. Every element had it, with the default
  NunitoSans, and it did next to nothing: the input in the inspector was commented out
  and additionally disabled, so it was never operable, and only two components read the
  value at all -- table and the formula area (text-area-math).
  Nothing renders differently. Two assistant templates set "Roboto" there, a font the
  player does not ship, but both sit on text elements, and the text component never read
  the property -- so those two rendered in the player's font before this change as well.
  On table and formula area the value has only ever been the default. (The framing in
  #1182, that the system substituted a font there, does not hold for that reason.)
  The property stays in stored units and is ignored from now on; it is dropped from the
  styling group on the next load, and no migration step is needed. Should a font choice
  return, it belongs on the unit rather than on each element (#921).

(#1226, no version raise -- a property group is retired, none is added)
- Image, geometry, trigger, hotspot-image, marking panel and likert row no longer have a
  styling group. Not one of their components ever read a styling value -- not even the
  background colour -- but the inspector offered six controls for each of them
  (background colour, font colour, font size, bold, italic, underline) whose values were
  stored and never used. In the shipped 2.x line these elements had no styling group
  either, and therefore no controls: the base class declared it optional and left it
  unset. The group appeared with the 3.0.0 beta, when normalization started building it
  for every element, so this restores the released behaviour rather than removing a
  feature. Values a beta-era unit stored on one of the six are dropped on the next load;
  nothing rendered them. Newly saved units carry an empty `"styling": {}` for these six.
  Should a background colour be wanted on an image or a geometry app, that is a feature
  of its own: the property would have to be USED, rather than offered and ignored.
  One editor detail follows from it: selecting one of the six together with a styled
  element now leaves no styling tab, because the merge keeps only what the whole
  selection shares. That was the behaviour of the 2.x line as well; in between, the
  text's font size stayed editable while an image was co-selected.

(#1230, no version raise -- styling members are retired, none is added)
- The two widget elements, molecule editor and periodic table, no longer carry font and
  border styling. They declared eleven styling members and applied two: the background
  colour and the font colour of the button that opens the widget. Font size, bold,
  italic, underline and the four border members had controls in the inspector that
  rendered nothing -- the borders around the periodic table's element squares come from
  the component's stylesheet, not from the model. Sixteen controls disappear, eight per
  widget. Stored values for them are dropped on the next load. No RELEASED version ever
  displayed them: the buttons did bind these eight values while they were mat-buttons,
  between 2026-02-26 (c8357781) and 2026-05-06 (fce5af06), but that window closed before
  the first beta -- both 3.0.0-beta tags already carry the mini-fab buttons with two
  colours. Both elements were added after the 2.x line, so unlike #1226 there is no
  earlier released behaviour to restore -- the rule is the same either way: no control
  for something the element cannot do.
  One editor detail follows, as it did in #1226: a widget selected together with a text
  element used to offer font size, bold, italic and underline, and those writes reached
  the TEXT element, which renders them. For that mixed selection only the two colours
  remain, so the text's font size is no longer editable while a widget is co-selected.
- Also gone, invisible either way: both widget templates bound `vertical-align` to
  `labelAlignment`, a property only the button element declares. The value was always
  undefined.
